## 1. ที่มาและเป้าหมาย

ร้านค้าบนแพลตฟอร์ม RAN-R-HAN ปัจจุบันให้บริการ 2 รูปแบบ:

- **ทานที่ร้าน (Dine-in):** ลูกค้าสแกน QR / ระบุโต๊ะ
- **รับกลับบ้าน (Takeaway):** ลูกค้าสั่งล่วงหน้า มารับเอง

ต้องการเพิ่มรูปแบบที่ 3:

- **ทางร้านจัดส่ง (Store Delivery):** ร้านส่งอาหารถึงบ้านลูกค้าโดยตรง (ไม่ผ่านแพลตฟอร์มกลาง เช่น Grab/Lineman)

บริบทเฉพาะของพื้นที่: **เขตเทศบาลเมืองแม่ฮ่องสอน** — พื้นที่เล็ก ชุมชนรู้จักกัน ร้านค้าส่วนใหญ่ส่งฟรีในเขตเทศบาลและพื้นที่ใกล้เคียง

## 2. แรงจูงใจ — "ช่วยไรเดอร์ท้องถิ่น"

ความตั้งใจเดิมคือต้องการช่วยไรเดอร์ที่วิ่งงานบน App ปัจจุบัน (Grab/Lineman) ให้มีรายได้จากการส่งงานร้านค้าท้องถิ่นโดยตรง โดยไม่ต้องถูกหักหัวคิว

### ❌ ข้อสรุปสำคัญ: ทุกแนวทาง "ช่วยไรเดอร์" มีจุดตาย

| แนวทาง | ปัญหาที่พบ |
|--------|-----------|
| Rider Web Link (ส่งลิงก์ให้ไรเดอร์กดรับงาน) | ต้องสร้างหน้าเว็บไรเดอร์, ยืนยันตัวตนยาก, ยกเลิกงานกลางคันได้ |
| LINE Job Share (ส่งข้อความเข้ากลุ่มไรเดอร์) | ไรเดอร์อัปเดตสถานะในระบบไม่ได้, พนักงานต้องมาคอยกดเอง |
| Speed Dial (สมุดไรเดอร์ประจำร้าน) | ปิดโอกาสไรเดอร์คนอื่น, ไม่ได้ช่วย "ชุมชนไรเดอร์" จริงๆ |
| **ทุกแนวทาง** | **ปัญหา "การกระจายงาน (Job Dispatching)" — แก่นของปัญหาที่แท้จริง** |

### ⚠️ ผลข้างเคียงที่ไม่ตั้งใจ

- ออเดอร์ที่เคยอยู่ใน Grab → ย้ายมา RAN-R-HAN → งานใน App น้อยลง → ไรเดอร์คนอื่นๆ (ที่ไม่ใช่คนที่ร้านโทรหา) เสียรายได้
- ช่วยได้เฉพาะบางคน แต่ทำร้ายคนอื่นในอาชีพเดียวกัน เพราะขาด "กลไกกระจายงานที่ยุติธรรม"

## 3. การวิเคราะห์เชิงลึก — ทำไม Delivery ถึงซับซ้อนกว่า Takeaway

### 3.1 Asymmetry ของการควบคุมเวลา

```
Takeaway:  ลูกค้าควบคุมเวลา → ร้านเตรียมของรอ → ทุกอย่างชัดเจน
Delivery:  ร้านต้องควบคุมเวลา → แต่ขึ้นอยู่กับไรเดอร์ → ไม่แน่นอน
```

### 3.2 ความเสี่ยง "เงินจ่ายแล้ว ไม่มีคนส่ง"

```
ลูกค้าโอน PromptPay → ร้านหาไรเดอร์ไม่ได้ → อาหารค้าง
```

- ระบบปัจจุบัน **ไม่มี Refund Flow** เลย
- ลูกค้าที่จ่ายแล้วและรอแล้วไม่ได้อาหาร = ความเสียหายต่อชื่อเสียงร้านสูงมาก
- เกิดได้ง่ายในวันฝนตก / เทศกาล / ไรเดอร์ไม่ว่าง

### 3.3 "Experience Gap" ทำให้ระบบแย่กว่าโทรสั่งธรรมดา

| จุด | โทรสั่งตรง | ใช้ระบบ (ไม่มี Logistics Layer) |
|-----|-----------|--------------------------------|
| ยืนยันส่งได้ | ร้านตอบทันที | รอ... ไม่รู้ |
| รู้ว่าไรเดอร์มา | ไรเดอร์โทรบอก | ระบบไม่รู้ |
| ETA | ร้านบอกได้คร่าวๆ | ไม่มีในระบบ |
| ปัญหา | โทรถามร้านได้ทันที | ระบบเงียบ ลูกค้างง |

### 3.4 Root Cause สุดท้าย

```
Delivery ≠ แค่เพิ่ม Order Type ใหม่
Delivery = ต้องการ Logistics Layer ใหม่ทั้งหมด
```

ทุกแพลตฟอร์มที่ทำ Delivery สำเร็จ (Grab, Lineman, Robinhood) ลงทุนกับ Logistics Layer นี้หนักมาก ไม่ใช่เพราะอยากทำ แต่เพราะ **ขาดไม่ได้ถ้าจะทำให้ใช้งานได้จริง**

## 4. แนวทางที่วิเคราะห์ไว้ (เรียงตามความซับซ้อน)

### ระดับ 1: ไม่เพิ่มตอนนี้ ✅ (เลือกแนวทางนี้สำหรับ MVP รอบนี้)

- Takeaway + Walk-in ทำงานสมบูรณ์แบบก่อน
- ลูกค้าที่ต้องการ Delivery ยังคงโทรสั่งตามปกติ
- รอ Feedback จากร้านทดลองจริงก่อนตัดสินใจ

### ระดับ 2: Delivery + Guard Rails (พิจารณาใน Phase 2)

- รับออเดอร์ Delivery ได้ แต่ **จ่ายเงินสดเท่านั้น** (ตัด PromptPay risk)
- ออเดอร์ขึ้น KDS เป็น Pending พิเศษ รอร้าน **โทรยืนยันกับลูกค้าก่อน**
- ร้านยืนยันได้ → กดรับออเดอร์ → เริ่มทำ
- ร้านยืนยันไม่ได้ → กดยกเลิก → ไม่มีปัญหาเรื่องเงิน

### ระดับ 3: Full Delivery (Phase 3+ ต่อเมื่อพร้อมจริงๆ)

- ต้องมีไรเดอร์ประจำร้านที่แน่นอน
- เพิ่ม PromptPay + Real-time tracking
- พิจารณา Refund Flow ก่อนเปิด

## 5. เงื่อนไขที่ต้องมีก่อนเปิด Delivery (Checklist)

ก่อนจะตัดสินใจ implement ให้ตอบคำถามเหล่านี้ได้ก่อน:

- [ ] ร้านมีไรเดอร์ประจำหรือพนักงานส่งของตัวเองหรือยัง?
- [ ] ร้านมีนโยบาย "ขอบเขตพื้นที่ส่ง" ชัดเจนแล้วหรือยัง? (รัศมีกี่กม.? ส่งฟรีหรือมีค่าส่ง?)
- [ ] มี Refund Flow สำหรับกรณีส่งไม่ได้หรือยัง?
- [ ] ร้านพร้อมรับภาระโทรยืนยันลูกค้าทุกออเดอร์ Delivery หรือยัง?
- [ ] ทดสอบ Takeaway + Walk-in ในร้านทดลองจนมั่นใจแล้วหรือยัง?

## 6. Schema ที่รองรับอยู่แล้ว (ไม่ต้องแก้เพิ่ม เมื่อถึงเวลา)

Schema ปัจจุบัน **รองรับ Delivery ไว้แล้วเกือบครบ** ไม่ต้องทำ migration ใหม่:

| สิ่งที่ต้องการ | ที่อยู่ |
|---|---|
| `orders.type = 'delivery'` | `20260906000001_pickup_mvp.sql` line 9 |
| `orders.delivery_address` | line 15 |
| `orders.delivery_lat/lng` | line 16–17 |
| `shops.allow_delivery` | line 29 |
| `create_pickup_order(p_delivery_*)` | RPC ใน migration เดิม |

Frontend ที่รองรับแล้ว:
- `CheckoutClient.tsx` — มี address form + GPS button ครบ
- `OrdersKDSClient.tsx` — มี Delivery Info Box (สีม่วง) + ปุ่ม Google Maps
- `SettingsClient.tsx` — มี toggle `allow_delivery` แล้ว

สิ่งที่ต้องเพิ่มเมื่อถึงเวลา:
- Refund Flow (สำคัญที่สุด ต้องมีก่อนเปิด PromptPay)
- "Pending Delivery Confirmation" state ใหม่ใน KDS
- ข้อความนโยบายพื้นที่จัดส่งในหน้า Checkout
- เปิด `allow_delivery = true` ใน Shop Settings

## 7. บทสรุป

> ปัญหาของ Delivery ไม่ใช่เรื่องโค้ด — Schema และ UI รองรับอยู่แล้ว
>
> ปัญหาคือ **"Logistics Layer"** ที่ต้องมีคนจริงๆ มาดูแลก่อนที่ระบบจะมีความหมาย
>
> เปิดใช้งาน Delivery ก็ต่อเมื่อ **ร้านค้ามีคนส่งที่ชัดเจนและมีนโยบายส่งที่ชัดเจน** เท่านั้น
> อย่าเปิดเพราะ "ระบบรองรับอยู่แล้ว" — เพราะความเสียหายจะตกที่ร้านค้า ไม่ใช่ที่โค้ด
