# แนวทางการแก้ไขแอป เพื่อรองรับข้อกำหนดกฎหมาย/PDPA — ฉบับร่าง (DRAFT)

> **สถานะ: ฉบับร่างแนวทาง (DRAFT) — เป็นเอกสารวางแผนเท่านั้น ยังไม่มีการแก้โค้ดจริงในโปรเจกต์**
> เอกสารนี้แปลงข้อกำหนดจาก [นโยบายความเป็นส่วนตัว](./RANRHANนโยบายความเป็นส่วนตัวDRAFT.md) และ [ข้อกำหนดการใช้งาน](./RANRHANข้อกำหนดการใช้งานDRAFT.md) (ฉบับร่างที่ทนาย/นักบัญชีทบทวนแล้ว) ให้เป็น**งานทางเทคนิคที่ต้องทำจริงในแอป** — ไม่ใช่คำแนะนำกฎหมาย เป็นเอกสารวิศวกรรมที่ต่อยอดจากผลตรวจสอบกฎหมายก่อนหน้า
> งานบางส่วนที่นี่**ทับซ้อน/เชื่อมโยงกับแผนพัฒนาหลัก** (`RAN-R-HAN-แผนพัฒนา-2026-09-10.md`, WP-1 ถึง WP-18) จะระบุจุดเชื่อมโยงไว้ในแต่ละข้อ เพื่อไม่ให้วางแผนซ้ำซ้อนกัน

---

## ภาพรวม: ช่องว่างทางเทคนิคที่พบ

จากการตรวจสอบระบบจริง (ไม่ใช่การคาดเดา) พบว่า **ตอนนี้แอปยังไม่มีกลไกทางเทคนิคใดๆ รองรับข้อกำหนดที่เขียนไว้ใน Privacy Policy/ToS ฉบับร่างเลย** — เอกสารนโยบายกับพฤติกรรมจริงของแอปยังเป็นคนละเรื่องกัน ต้องปิดช่องว่างนี้ก่อนเผยแพร่นโยบายใช้งานจริง มิฉะนั้นนโยบายจะกลายเป็นการเขียนสิ่งที่ระบบไม่ได้ทำจริง (ซึ่งมีความเสี่ยงทางกฎหมายมากกว่าไม่เขียนเลย)

---

## WP-19: หน้าเว็บจริงสำหรับ Privacy Policy และ Terms of Service

**สถานะปัจจุบัน:** เอกสารทั้งสองมีอยู่แค่เป็นไฟล์ `.md` ใน `docs/` ลูกค้าที่ใช้แอปจริงเข้าไม่ถึงเลย

**งานที่ต้องทำ:**
- สร้าง route ใหม่ เช่น `/[slug]/privacy` และ `/[slug]/terms` (หรือ path ที่ไม่ผูกกับร้านถ้าจะใช้ฉบับเดียวกันทุกร้าน — ต้องตัดสินใจว่านโยบายเป็นระดับแพลตฟอร์มหรือระดับร้าน เพราะแต่ละร้านมี `[ต้องกรอก]` เช่น ชื่อนิติบุคคล/ช่องทางติดต่อ ต่างกัน)
- Render เนื้อหาจาก Markdown เป็นหน้าเว็บอ่านง่าย (ตัด `[ต้องกรอก]`/หมายเหตุภายในออกจากเวอร์ชันที่ลูกค้าเห็น — เอกสารร่างที่มีคำเตือน DRAFT ควรอยู่แค่ใน `docs/` เท่านั้น)
- เพิ่มลิงก์ในหน้า footer ของหน้าเมนูลูกค้า (`src/app/[slug]/page.tsx`, `MenuClient.tsx`) และหน้า checkout

**Priority:** สูง — ไม่มีหน้านี้ = นโยบายที่เขียนไว้ไม่มีผลในทางปฏิบัติ เพราะลูกค้าไม่มีทางเห็น
**เชื่อมโยง:** ทำพร้อม Phase 2 ของแผนพัฒนาหลัก (ซิงก์เอกสาร)

## WP-20: จุดขอความยินยอม (Consent UI) และบันทึก Consent ที่หน้า Checkout

**สถานะปัจจุบัน:** ปุ่ม "Get GPS" เรียก `navigator.geolocation` ของเบราว์เซอร์ตรงๆ — ได้แค่ browser permission prompt มาตรฐาน **ไม่มีการบันทึกลงระบบว่าลูกค้ายินยอมเมื่อไหร่** และไม่มี checkbox ยอมรับ ToS/Privacy Policy ก่อนกดสั่งซื้อเลย

**งานที่ต้องทำ:**
- เพิ่ม checkbox "ยอมรับข้อกำหนดการใช้งานและนโยบายความเป็นส่วนตัว" (พร้อมลิงก์ไปหน้า WP-19) ก่อนปุ่มยืนยันสั่งซื้อในหน้า checkout — ห้ามกดสั่งซื้อได้จนกว่าจะติ๊กยอมรับ
- เพิ่มคอลัมน์บันทึกเวลา (เช่น `orders.consent_accepted_at`) หรือสร้างตาราง `consent_log` แยก (เก็บ `order_id`, `consent_type`, `accepted_at`) — ควรใช้ migration ใหม่ ไม่แก้ migration เก่า ตามกฎเหล็กของโปรเจกต์
- สำหรับ GPS: หลังผู้ใช้กด allow ใน browser prompt สำเร็จ ให้บันทึก flag/timestamp ว่ายินยอมแชร์ตำแหน่งเมื่อไหร่ (ไม่ต้องเก็บพิกัดซ้ำซ้อน แค่หลักฐานว่ามีการยินยอมจริง)

**Priority:** สูง — เป็นหลักฐาน (evidence) ที่จำเป็นถ้าเกิดข้อพิพาทว่าลูกค้ายินยอมหรือไม่ ไม่มีระบบนี้ = ไม่มีหลักฐานพิสูจน์ความยินยอมเลย
**เชื่อมโยง:** งานใหม่ ไม่ซ้ำกับ WP เดิมในแผนพัฒนาหลัก

## WP-21: Audit Log สำหรับการนำเข้าข้อมูลจากคอมเมนต์ Facebook

**สถานะปัจจุบัน:** `src/app/actions/delivery.ts` (ระบบพรีออเดอร์) ไม่มีการบันทึกว่าพนักงานคนใดนำเข้าข้อมูลรอบใดเมื่อไหร่เลย — **และตามที่ตรวจพบในรายงานความปลอดภัยก่อนหน้านี้ (SEC-E02) ฟังก์ชันเหล่านี้ยังไม่มีการเช็คสิทธิ์/ตัวตนผู้เรียกเลยด้วยซ้ำ** จึงยังไม่มีแม้แต่ข้อมูล "ใคร" ให้บันทึก log ได้

**งานที่ต้องทำ:**
- **ทำหลัง WP-2 ของแผนพัฒนาหลักเท่านั้น** (เพิ่ม `auth.getUser()` เข้า `delivery.ts`) เพราะต้องรู้ตัวตนผู้เรียกก่อนถึงจะบันทึก log ได้ว่าใครทำ
- หลังจากนั้น เพิ่มการบันทึก audit log ทุกครั้งที่มีการนำเข้าพรีออเดอร์แบบ bulk จากคอมเมนต์ Facebook (`addBulkPreorderItemsAction`) — เก็บ `imported_by_user_id`, `round_id`, `imported_at`, จำนวนรายการที่นำเข้า
- เพิ่ม checklist/คำเตือนในหน้า admin เปิดรอบพรีออเดอร์ ให้พนักงานแปะข้อความ consent (จากภาคผนวกของ ToS) ในโพสต์ Facebook ก่อนเปิดรับคอมเมนต์ — ไม่จำเป็นต้องเป็นระบบอัตโนมัติ แค่ UI reminder/checklist ก็เพียงพอสำหรับ MVP

**Priority:** สูง — เชื่อมโยงกับจุด 🔴 ที่ทนายระบุว่าต้องตรวจสอบก่อนเผยแพร่ (accountability ของข้อมูลจากคอมเมนต์)
**เชื่อมโยง:** ต่อยอดจาก **WP-2** ของแผนพัฒนาหลัก — ควรวางแผนทำในรอบเดียวกัน

## WP-22: ระบบลบ/Anonymize ข้อมูลอัตโนมัติ (Data Retention Automation)

**สถานะปัจจุบัน:** ไม่มีระบบลบข้อมูลอัตโนมัติเลยในโปรเจกต์ — ทุกอย่างที่เก็บเข้าฐานข้อมูลจะอยู่ถาวรจนกว่าจะมีคนลบมือ

**งานที่ต้องทำ** (อิงตามตารางระยะเวลาในนโยบายความเป็นส่วนตัว ข้อ 7):
- สร้าง scheduled job (ตัวเลือก: Supabase `pg_cron`, หรือ Vercel Cron เรียก API route) รันเป็นรอบ (แนะนำทุกวัน) เพื่อ:
  - ลบ/anonymize คำสั่งซื้อที่ยกเลิกก่อนชำระเงิน (`orders.status = 'cancelled'` ที่ไม่เคยมี payment สำเร็จ) ที่เก่ากว่า 90 วัน
  - ลบข้อมูลดิบจากคอมเมนต์ Facebook ที่ไม่ได้กลายเป็นออเดอร์สำเร็จ เก่ากว่า 90 วัน
  - ลบ security/access log ที่เก่ากว่า 1 ปี (ต้องมีระบบ log นี้อยู่ก่อน — ดู WP-21 และงานความปลอดภัยในแผนหลัก)
- **ข้อมูลบัญชี/ภาษี (payments, orders ที่ชำระเงินสำเร็จ) — แนะนำ "ยัง"ไม่ตั้งให้ลบอัตโนมัติ** ในเฟสนี้ แม้จะครบ 5-7 ปี เพราะความเสี่ยงจากการลบผิดพลาด/ก่อนเวลาอันควรสูงกว่าการเก็บไว้เกิน — ให้ระบบแค่ flag ว่ารายการไหนครบกำหนดแล้ว รอเจ้าของร้านอนุมัติลบด้วยมือ (manual review ก่อน auto-delete)

**Priority:** ปานกลาง-สูง — ยิ่งไม่มีระบบนี้นาน ยิ่งมีข้อมูลสะสมเกินความจำเป็นมากขึ้นเรื่อยๆ ซึ่งขัดหลัก PDPA โดยตรงและเพิ่มความเสียหายหากมีข้อมูลรั่วไหล
**เชื่อมโยง:** งานใหม่ ไม่ซ้ำกับ WP เดิม แต่ควรทำหลัง Phase 1 (ความปลอดภัย) ของแผนหลักเสร็จก่อน เพื่อไม่ให้ scheduled job ตัวใหม่กลายเป็นอีกจุดที่ไม่มีการเช็คสิทธิ์

## WP-23: กลไกรองรับการใช้สิทธิของเจ้าของข้อมูล (Data Subject Rights)

**สถานะปัจจุบัน:** ไม่มีช่องทางให้ลูกค้าขอเข้าถึง/แก้ไข/ลบ/โอนย้ายข้อมูลของตัวเองในระบบเลย

**งานที่ต้องทำ (ระดับ MVP พอสำหรับร้านเดียว ไม่ต้องสร้าง self-service UI ซับซ้อน):**
- ใส่ช่องทางติดต่อ (อีเมล/เบอร์โทร) ในหน้า Privacy Policy (WP-19) ให้ลูกค้าติดต่อขอใช้สิทธิได้
- เจ้าของร้าน/Superadmin ดำเนินการตามคำขอผ่าน Supabase dashboard ได้โดยตรงในเฟสนี้ (ปริมาณคำขอของร้านเดียวไม่น่าจะมาก ยังไม่จำเป็นต้องสร้างระบบอัตโนมัติ)
- **แต่ต้องมีที่บันทึก log คำขอ** (แม้จะเป็นแค่ spreadsheet/บันทึกง่ายๆ นอกระบบก่อนก็ได้) — วันที่ขอ, สิทธิที่ขอใช้, วันที่ดำเนินการเสร็จ เพื่อพิสูจน์ compliance ย้อนหลังได้

**Priority:** ปานกลาง — ความเสี่ยงต่ำขณะมีลูกค้าไม่มาก แต่ควรมีกลไกพื้นฐานไว้ก่อนเปิดกว้างขึ้น
**เชื่อมโยง:** งานใหม่ ไม่ซ้ำกับ WP เดิม

## WP-24: ผลกระทบทางเทคนิคจากการตัดสินใจ Controller/Processor

**สถานะปัจจุบัน:** ยังไม่มีคำตอบ (รอทนายวิเคราะห์ร่วมกับเจ้าของระบบ ตามที่ระบุในนโยบายความเป็นส่วนตัว ข้อ 6)

**งานที่ต้องทำ (ขึ้นกับผลตัดสินใจ — ยังทำไม่ได้จนกว่าจะมีคำตอบ):**
- ถ้าผลสรุปว่าแพลตฟอร์มเป็น **Processor** ให้ร้าน: อาจต้องมีสัญญา Data Processing Agreement (DPA) แนบท้ายสัญญา B2B (WP ใหม่ที่ยังไม่มีในแผนหลัก — เกี่ยวข้องกับ "สัญญา B2B" ที่เคยเสนอไว้ในเอกสารภาพรวมกฎหมาย)
- ไม่ว่าผลจะเป็นสถานะใด **audit log ที่ครบถ้วนสำหรับการเข้าถึงข้ามร้านของ Superadmin คือสิ่งที่ต้องมีอยู่ดี** เพื่อพิสูจน์ accountability — งานนี้ทับซ้อนโดยตรงกับ **SEC-E01/SEC-E02** (ช่องโหว่ auth-bypass) ที่ระบุไว้ใน Phase 1 ของแผนพัฒนาหลักแล้ว ไม่ต้องเปิดงานใหม่ซ้ำ

**Priority:** รอผลตัดสินใจทางกฎหมายก่อน จึงจะประเมิน priority ทางเทคนิคที่แท้จริงได้
**เชื่อมโยง:** ขึ้นกับ **WP-1/WP-2** ของแผนพัฒนาหลัก โดยตรง

## สรุปลำดับการทำงาน (ผูกกับ Phase ของแผนพัฒนาหลัก)

| Phase | งานในเอกสารนี้ | เหตุผล |
| --- | --- | --- |
| Phase 1 (ความปลอดภัย — ทำก่อนสุด) | WP-21 (audit log พรีออเดอร์, ทำหลัง WP-2), ส่วน audit log ของ WP-24 | ต้องมีตัวตนผู้ใช้ที่เช็คแล้วก่อน ถึงจะบันทึก log ได้ถูกต้อง |
| Phase 2 (ซิงก์เอกสาร) | WP-19 (หน้าเว็บ Privacy/ToS), WP-20 (consent UI) | ต้องมีหน้าให้ลิงก์ไปหาก่อนจะขอ consent ได้จริง |
| Phase 3 (เทสต์/โครงสร้าง) | WP-22 (ระบบลบข้อมูลอัตโนมัติ) | ควรมี test coverage ที่มั่นคงก่อนเพิ่ม scheduled job ที่ลบข้อมูลจริง |
| Phase 4 (รอตัดสินใจเจ้าของ/ทนาย) | WP-23 (สิทธิเจ้าของข้อมูล), WP-24 (Controller/Processor) | ขึ้นกับการตัดสินใจที่ยังไม่เกิดขึ้น |

**ข้อควรระวังสุดท้าย:** เอกสารนี้เป็นแผนงานเท่านั้น ยังไม่มีการเขียนโค้ดใดๆ ทั้งสิ้น หากต้องการให้เริ่มลงมือพัฒนาจริงตาม WP ข้อใด ต้องแจ้งขอให้เริ่มงานเขียนโค้ดแยกเป็นคำขอใหม่
